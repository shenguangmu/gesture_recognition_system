### P1 · PS 侧基线（**唯一能补齐 20 分项的动作**）

> ✅ **板已到、overlay 已能加载、串口与网络都已打通** ——
> 这件事现在**只需要在板上跑一次脚本**，没有任何前置阻塞。

| 步骤 | 做法 |
|---|---|
| 1 | 把 [`../host/bench_ps_baseline.py`](../host/bench_ps_baseline.py) 拷到 PYNQ（`scp` 在 **PC** 上跑） |
| 2 | 板上跑：`sudo -E /usr/local/share/pynq-venv/bin/python3 bench_ps_baseline.py --json ps.json` |
| 3 | 与 PL 侧延迟对比 → **加速比** |

> **PL 侧的口径是现成的**：`design.md` §4.4 的上板实测 **≈5 ms/帧**。
> ⚠ 对比时要说清这一项**不含摄像头采集**（输入来自 DDR 测试图），
> 以及它是 PL 侧单次预处理延迟，不是端到端帧率。

**为什么是唯一的**：它直接回答赛题的核心问题"**为什么用 FPGA**"。
其余各项（资源、时序、优化尝试）**都已经做到能做的最好**了。

**可对照的先例**：CANDAR 2020 在 **PYNQ-Z1** 上测得
"**相比同一块板的 PYNQ ARM CPU 加速 22×**"（见 `design.md` §1.4②）。
本作品测出的数可与 22× 对照。

> ⚠ **主机 CPU 的数不能直接写进报告**。该脚本在 PC 上跑出约 3.8 ms/帧，
> 但那是 Ryzen 9 8940HX，**不是 Cortex-A9**，差着代际。
> 脚本里已标注它是"主机参考值，非 PS 基线"。

> ⚠ **PL 侧那一半要取对口径**。`design.md` §4.4 的**逐级**表是
> **从 instance 表加总的估算**（顶层 `DATAFLOW` 的 latency 在 csynth 里
> 显示为 `?`，各 stage 重叠，HLS 给不出静态总延迟）。
> **权威数字是上板实测的 ≈5 ms/帧**，拿估算值去除以 PS 基线会被挑。
>
> ⚠⚠ 该表**曾经把 `crop_scale` 记成 20.74 ms / 整链 21.4 ms** ——
> 那是把 `LOOP_TRIPCOUNT` 的**循环上界**当成了实际拍数。
> **2026-09-21 上板实测更正为 3.07 ms / 整链 ≈3.7 ms**（与实测 5 ms 吻合）。
> **比加速比之前先确认这张表是当前版本**，否则会高估 PL 侧延迟一个数量级。

### P3 · HLS 优化前后对比 ✅ **已完成（2026-09-18）**

结果见 [`../src_hls/optimization-report.md`](../src_hls/optimization-report.md)。
**结论是负结果，但数据完整**：

- 探针证明 DSP 的根因（腐蚀流水线的索引算术：71 → 15）
- 但**改不掉**：换编译期步长无效、手写展开反而更差（71 → 86）
- **顺带查出 WNS `+0.265` 不属于本设计**，是 AMD `v_tc` IP 的
- **顺带核对出 3 处凭记忆写错的资源数字**（LUT `13,184`→`13,144`、
  Fmax `137`→`143.31 MHz`），已更正
- 工具用上了：[`../skill/pynq/golden_compare.py`](../skill/pynq/golden_compare.py)，
  同时**发现并修掉了它的一个静默失败**（见 `skill/pynq/README.md`）

> ⚠ **DSP 的大头在 `morph_stage`（56 个），不在 `thresh_stage`（2 个）。**
> 项目里曾有四处写反。
>
> ⚠ **旧警告已作废**：这里原先写"唯一能降 DSP 的改法会让 II 从 1 退化成 2"。
> 经 2026-09-18 实测，**从未出现过 II=2**（全程 II=1），
> 而能降 DSP 的写法代价是**资源反而增加**（71→86）。详见 `optimization-report.md`。
